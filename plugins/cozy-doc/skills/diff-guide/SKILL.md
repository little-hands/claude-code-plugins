# diff-guide

差分を、**上から順に読めば理解できる形**にする。`git diff` は変更を機械の都合（パス順）で並べるが、人が読む順は依存の順。その並べ替えと「なぜ今これを読むのか」を足すのがこのスキル。

## 0. 引数と対象の決め方

| 引数 | 対象 | 取り方 |
|---|---|---|
| なし（既定） | 未コミットの変更 | 追跡分は **`git diff HEAD`**（`git diff` はステージ済みを出さない）。未追跡は `git ls-files --others --exclude-standard` でファイル単位に展開してから `git diff --no-index -- /dev/null <path>` |
| PR 番号 / URL | GitHub の PR | `gh pr diff <番号>`。本文・会話・レビューは `gh pr view <番号> --json title,body,comments,reviews`（行コメントが要るなら `gh api repos/{owner}/{repo}/pulls/<番号>/comments`） |
| `<base>...<head>` | ブランチ間 | `git diff <base>...<head>`（**3 点**。分岐点からの差分。ユーザーが 2 点で渡してきても 3 点で叩く — 2 点だと base 側の後続コミットが削除として混ざる） |

**`git diff --no-index` は差分があると終了コード 1 を返す**（`grep` と同じ流儀）。失敗ではないので、そのまま読み進める。

**引数が無くて未コミットの変更も無いときだけ**、`AskUserQuestion` で対象を聞く（選択肢には ⭐ の推奨度と理由を添える）。直前に自分が書いた変更・直前に読んだ PR があるなら、聞かずにそれを対象にして進む。

**出力先は `/tmp/diff-guide-<YYYYMMDD-HHMM>-<slug>.html`**（時刻の取り方は手順 3）。 `<slug>` は対象がわかる英小文字ケバブ（`ep-004-11-pbi1-4`、`pr-512`、`refactor-ports`）。書いたら `open` する。
**ユーザーが置き場所を指示したらそこに書く。** リポジトリ内へ置くよう言われたら、そのリポジトリの文書規約（`docs/` の置き場・命名）に従う。

## この構成の芯

差分を渡された人が最初に困るのは「どこから読むか」で、次に困るのが「これは読まなくていいのか」。だから**読む順を宣言し、1 ファイル 1 節に割り、各節の頭に「なぜ今これを読むのか」を 1 文置く**。

守る原則は 4 つ。

1. **読む順は依存の順**（型 → それを使う側 → それを束ねる側）。`git diff` の出力順・パスのアルファベット順で並べない
2. **diff は全文を貼らない。** 読みどころだけ抜き、落とした部分は `.snip` で「何を落としたか」を書く
3. **消えたもの・探しても無いものを先に断る**（`.callout`）。読み手が探し回る時間をゼロにする
4. **`.status-row` には機械で確かめた事実だけを数字で置く**（テストの件数・リンタの errors 数・コミットの有無。失敗した数値は `.ng` で赤くする）。確かめていない項目は行ごと消す

## 使わない場面

- **差分そのものが見たいだけ** — `git diff` / `gh pr diff` の出力をそのまま返す
- **レビュー（欠陥探し）が目的** — `/code-review` か `/review:phase` へ。このスキルは「読ませる」ためのもので、指摘を作る場ではない。**既にレビュー結果があるなら末尾の表に載せる**（自分で新しく指摘を作らない）。深刻度は `.sev.must` / `.should` / `.consider`、対応が済んだ行は `<tr class="done">` ＋ `.sev.done`
- **変更が 1 ファイル・数行** — 本文に diff を貼って 2〜3 行説明すれば足りる

## 手順

### 1. 差分を取る

引数に応じて上の表のコマンドを叩く。**全ファイルの diff を最後まで読む。** 抜粋を選ぶには全体を知っている必要がある。

同時に、**その差分について既に分かっている機械的事実**を集める（あれば）:

- テストの実行結果（テストランナーが最後に出す 1 行。`pytest -q` なら `N passed in Xs`）
- リンタ・リンクチェック等の結果
- コミット済みか未コミットか
- レビュー結果（このセッションで `/review:phase` や `/code-review` を回していれば、その指摘）

**無い項目は集めに行かなくてよい。** ただし**テストを勝手に走らせて時間を使わない** — 既に結果があるものだけ載せる。

### 2. 読む順を決める

依存の向きで並べる。判定は 1 問: **その節を読むのに、前の節の知識が要るか。**

| 型 | 並び |
|---|---|
| 新しい層・機能を足した | 型・定数 → それを作る側 → それを使う側 → 束ねる側 → 配線 |
| 既存を直した | 壊れていた場所 → 直した場所 → 波及して直した場所 |
| 設定・スクリプト | 入口（叩かれるもの）→ その中で呼ばれるもの |

**テストファイルは独立した節にしない。** 対応する実装の節の中で「テストで何を確かめているか」を 1〜2 行触れる。テストを主役にすると、読み手が実装を読む前にテストを読むことになる。

### 3. テンプレートから組み立てる

出力先を決める。**シェル変数に入れない** — Bash ツールは呼び出しごとに別のシェルなので、変数は次の手順まで残らない。

```bash
date +%Y%m%d-%H%M
```

これを 1 回叩き、返ってきた値で `/tmp/diff-guide-20260908-1530-<slug>.html` のような**実パスを確定させる**。以降の手順（Write・`grep`・`open`）は、そのリテラルのパスをそのまま書く。

テンプレートは**このスキルの Base directory 配下**にある（起動時に表示される `Base directory for this skill: ...` の値を先頭に付ける。固定パスで書かない — ユーザー単位のスキルかプラグイン経由かでインストール先が変わる）。`assets/template.html` を Read し、`{{...}}` を埋めた**全文を Write で出力先に書く**（UTF-8）。

テンプレートは**骨組みが 1 つずつ入っているだけ**なので、数に合わせて増減させる:

- `section.step` … 読ませるファイルの数だけ複製する（`1 / N` の N は総数）
- `.status-row > span` … 確かめた事実の数だけ。**確かめていない項目の行は消す**
- `nav.toc` の `li` … 節の数だけ
- `.diff` の中の `.line` … 抜粋した行の数だけ（`add` / `del` を使い分ける）
- `.callout` … 必要な節にだけ。無い節では丸ごと削る
- レビューの `section#review` … レビュー結果がある回だけ。無ければ丸ごと削る

**プレースホルダは 1 つも残さない。** `{{TITLE}}` は `<title>` と `<h1>` の 2 箇所にある。

#### 文書レベルのプレースホルダ

| 名前 | 中身 |
|---|---|
| `{{EYEBROW}}` | 対象の識別（`EP-004-11 訳抜けと追加の検査 — 実装メモ`、`PR #512 — レビュー前の下読み`） |
| `{{TITLE}}` | この差分を一言で（`いま出来ている実装（PBI-1〜4）の読み方`） |
| `{{LEDE}}` | **何が入っていて何が入っていないか**を 1〜2 文。読み手の期待をここで揃える |
| `{{TOC_ORDER_REASON}}` | 読む順をどう決めたか（`依存の順そのもの`、`壊れていた場所から`） |
| `{{TOTAL}}` | **節の数**（読ませないファイルは数えない） |
| `{{REVIEW_SOURCE}}` | レビュー表の出どころ（`/review:phase（Fable）の結果`） |
| `{{REVIEW_ROLE}}` | レビュー表の読み方 1 文（`成果物は直っていない — 指摘表そのまま`） |
| `{{FOOTER}}` | 追える先（対象のコミット・PR 番号・レビュー報告の在り処） |

**節にしないファイルがあるなら、`nav.toc` の `ol` の下に `<p>` を 1 つ足して「読まなくていいもの: …（理由）」と書く。** 黙って落とすと、読み手は差分の総数と節の数が合わないことに気づいて探し始める。

#### 各節に書くこと

| 要素 | 中身 | 落ちている形 |
|---|---|---|
| `.num` | `N / 総数 — 新規` / `— 変更` / `— 削除` | — |
| `h2` | ファイル名 ＋ `<code>` にディレクトリ | パス全部を h2 に書いて折り返す |
| `.role` | **なぜ今これを読むのか**を 1 文（斜体で出る） | ファイルの説明を書く（それは次の段落の仕事） |
| 本文 `p` | **どこを見ればいいか**。1〜2 段落 | diff を日本語に翻訳しただけ |
| `.diff` | 読みどころの抜粋 | 全文を貼る／読みどころ以外も貼る |
| `.callout` | 引っかかりそうな点・消えたもの（青）。**既知の穴・危険は `.callout.watch`**（赤） | 節ごとに義務的に付ける |

**`.role` を「〜を実装したファイル」で埋めない。** 読み手が知りたいのは「この節を飛ばすと後で困るか」。

### 4. diff の抜粋を作る

**行番号は新しいファイル側の行番号**を書く。抜粋の間を飛ばしたら `.snip` を挟み、**何を落としたか**を書く（`⋯ import と定数 ⋯`）。

```html
<div class="diff">
  <div class="filebar">🆕 <span class="new">new file</span> · finding.py · 32 行</div>
  <div class="lines">
    <div class="line add"><span class="ln">10</span><span class="txt">class Viewpoint(StrEnum):</span></div>
    <div class="line add"><span class="ln">11</span><span class="txt">    JAPANESE_REMAINING = "TCA-2-3"</span></div>
  </div>
  <div class="snip">⋯ 中略の説明 ⋯</div>
  <div class="lines">
    <div class="line del"><span class="ln">44</span><span class="txt">def is_resolved(...):</span></div>
  </div>
</div>
```

- **連続する行は 1 つの `.lines` にまとめる。** `<pre>` は使わない（中に `<div>` を置くと HTML として不正で、行の間に空行が出る）
- `+` `-` の記号は **CSS が付ける**（`.txt::before`）。テキストに書かない
- `<` `&` は `&lt;` `&amp;` にエスケープする（型注釈の `-> str | None`、ジェネリクスでよく踏む）
- `.filebar` は 3 変種 — `🆕 new file` / `✏️ changed` / `🗑 deleted`（クラスは `new` / `mod` / `gone`）＋ 行数。**リネームは `mod` に寄せ、`.role` か `.callout` で旧パスを書く**
- **行番号は新側。** `del` 行と削除ファイルは旧側の行番号を書く（新側に対応する行が無いため）
- **空行を表す `.line` は `<span class="txt"></span>` で置く**（抜くと詰まって読みにくい）
- 1 つの節に `.diff` を複数置いてよい（離れた 2 箇所を見せるとき）。ただし**合計 40 行を超えたら抜粋の選び方が粗い**

### 5. 自分で見直す（必須）

**まず機械で判定できるものを潰す**（目視より確実）。`<Base directory>` は起動時に表示される値。

```bash
python3 <Base directory>/assets/check.py <出力先パス>
```

`RESULT=ok` を確認する。NG の中身は 4 種 — 未置換のプレースホルダ / タグの閉じ忘れ・入れ子の不一致 / `<pre>` の中の `<div>`（`.lines` を使う）/ 未定義の CSS 変数。
**`no_steps=1` が出たら節を 1 つも拾えていない** — 中身が無いのではなく記法がずれている（`<section class="step">`）。

**そのうえで、書いたファイルを Read して読み直す。** 観点は 2 つ。

**間違いがないか**

- [ ] **抜粋した行が、実際の差分と 1 文字も違わないか。** 記憶で書いた行が混ざっていないか
- [ ] **行番号が新しいファイル側と合っているか**
- [ ] **`.status-row` の数字が、実際に叩いた出力と一致するか。** 叩いていない項目が載っていないか
- [ ] **レビュー表の指摘が、実際に出た指摘そのままか**（自分で足していないか）

**わかるか**

- [ ] **上から順に読んで詰まらないか。** 後ろの節で初めて出る型・関数を、前の節が使っていないか
- [ ] **各節の `.role` が「飛ばしていいか」に答えているか**
- [ ] **プレースホルダ（`{{`）が残っていないか**（`grep -c '{{[A-Z_0-9]*}}' <出力先パス>` が 0。0 件のとき grep は終了コード 1 を返すが、それが合格）
- [ ] **落とした部分に `.snip` が付いているか。** 黙って飛ばしていないか

### 6. 開いて伝える

確定させた出力先パスを `open` した上で、メッセージ本文で報告する。

- **どの順に並べたか・その理由**（1〜2 行）
- **抜粋で落とした大きな塊があれば、それを名指しで**
- **`.status-row` に載せられなかった項目**（テストを走らせていない等）があれば、そう言う

## 注意

- **UTF-8 で書く。** 文字化けしたら削除して Write で作り直す
- `pre` の中は**インデントがそのまま出る**。HTML の整形都合で字下げしない
- **`/tmp` の中身は消える**（macOS は最終アクセスから 3 日、再起動でも消える）。あとから参照したいと言われたら、リポジトリ内の恒久的な置き場所を提案する
- 🚨 **秘密情報を貼らない。** 差分に API キー・接続文字列・顧客データが含まれていたら、その行は抜粋から外し、外したことを本文に書く
- 配色はライト／ダークの両方を CSS 変数で持っている。**新しい色を直値で足さない**
